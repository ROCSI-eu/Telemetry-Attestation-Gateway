# AGENTS.md — Telemetry Attestation Gateway

## Authority and autonomy
- Treat current `main` and owning documents as authoritative; check affected files, PRs, issues, authorizations and relevant gates before edits.
- Continue already-authorized synthetic, isolated, reversible local exploration autonomously; do not invent dependencies on external reviewers or repeatedly request the same approval.
- Use a focused branch/PR, existing checks, concise evidence and an explicit checkpoint. Report only tests actually run. Follow the contribution policy effective at the time; never forge a DCO sign-off.

## Reuse verified checkpoints; avoid repetitive gates
- Carry forward the last accepted checkpoint with its **source, exact commit or deployment identity, scope, result and observed date**. A new chat, turn or handoff does not invalidate existing PASS evidence, accepted operational setup or previously granted scope. Label reused checks as *previously verified*, never newly executed.
- Investigate **only the state that can change the next decision**. Do not repeat unchanged CI, browser/QA suites, artifact checks, Cloudflare settings screenshots, rollback inventories or full preflight reports just because another step begins. Recheck when affected inputs change, evidence conflicts, material operational state changes or an imminent authorized action depends on a fresh fact.
- Distinguish **versioned facts** (source/build configuration and tested assets at a pinned SHA), **accepted baseline decisions** (hosting architecture and authorized scope) and **mutable live state** (current Production deployment, Cloudflare branch controls, viable rollback, CI). Reuse the first two until superseded; never report the third as newly confirmed without evidence.
- For TAG Mission Control, reuse the accepted Cloudflare Pages project `tag-mission-control`, branch `main`, static build `python3 showcase/build.py --out-dir dist`, canonical RO `/ro/`, EN `/en/` and root `/` → `/ro/` redirect as the routing baseline. Production/Preview automatic deployment settings have changed over time; **OFF is not an invariant**. A GitHub Cloudflare Pages SUCCESS check does not establish the currently served custom-domain SHA.
- **Read-only and code-only requests:** check only the requested delta and applicable HEAD/CI; do not demand another Cloudflare dashboard review, rollback proof, DNS audit or Production acceptance without an impending release action. Cite already verified, unchanged checkpoints concisely.
- **At an actual release-critical action**, perform a single focused fresh check of exact source/target and only the mutable facts needed to avoid wrong-version publication, unintended automatic deployment, duplicate deployment or loss of rollback. Consider a known auto-deploy side effect **before merging** and require authorization covering that consequence. If the target SHA is already live, continue to acceptance rather than redeploy. Ask once for missing account-only evidence, not at every handoff.
- **TAG Pages GitHub-to-Production evidence:** If an accepted checkpoint establishes Production `main` automatic deployments enabled and Preview deployments disabled, an explicitly authorized merge is the single deployment trigger; do not additionally deploy or retry manually. The Cloudflare Pages GitHub App `SUCCESS` check on the exact merged SHA confirms the provider-reported deployment, **not** the version currently served on the custom domain. Confirm the live domain separately with focused HTTP checks (RO/EN, redirects, CSP, noindex and share metadata), compare served assets with a build pinned to that SHA when appropriate, and use Chromium on Qube for changed responsive or animation behavior. Reuse unaffected PASS checks instead of repeating full suites or asking for routine screenshots.
- **TAG Pages account-only and rollback evidence:** Reuse the last accepted, dated Cloudflare branch-control and Production-deployment-history checkpoint while there is no material contradictory change. A previous successful Production deployment is a rollback *candidate*, not proof that rollback was executed or remains guaranteed. Request fresh dashboard/API evidence only if necessary evidence is missing, conflicting or materially stale for the specific release gate, or an explicitly required rollback cannot otherwise be established. Stop the affected action if a mandatory gate remains unverified; do not provision Cloudflare credentials or request new screenshots merely to repeat accepted checks.
- Never skip explicit approval, applicable rulesets or protection required for GitHub writes, merge, Production changes or evidence promotion; never bypass gates. If a material execution gate cannot be established, name that blocker and stop only the affected operation.

Do not include unverified work, private values, inflated status, or cosmetic journal churn for routine refactors.

## Qube Dev1: reusable QA tooling vs disposable runtime
- Keep verified, version-pinned development inputs (ArduPilot/SITL source and binary, TAG source at an exact commit, Nargo, Barretenberg, and public CRS) in dedicated unprivileged **persistent QA toolchain/source** paths, separate from each experimental runtime. Reuse a matching version/SHA-256 checkpoint rather than re-download or re-provision; missing, changed, unverified, or incompatible inputs fail closed until separately authorized. Never install these into global system paths or Production.
- Restrict writable experiment state to an owned, bounded, disposable runtime: stop and reap processes, release loopback sockets, and remove private captures, telemetry, witnesses, generated proofs, scratch, logs, and temporary runtime files. Cleanup must verify the exact runtime path and ownership and **must not delete** pinned binaries, sources, or CRS caches. Retiring or updating persistent versions needs its own explicit scope; avoid unbounded retention.
- Persistent tooling does **not** make a sandbox persistent or authorize execution: retain isolated network namespaces, host read-only except explicitly authorized QA writable paths, receive-only/no-MAVLink-command boundaries, offline proving/verification after separately approved public dependency provisioning, and the existing evidence/Production gates. Track packaging and resource/retention decisions in #88.

## Safety and evidence
- Synthetic experiments only; no real telemetry, hardware, MAVLink command generation/forwarding, production systems, live ledgers, participant data, or external sensitive operations without their separately authorized gates.
- No secrets, raw telemetry, witnesses, exact private values, stable identifiers or participant/customer material in Git, logs, UI, exports or receipts.
- All experimental outputs remain `EXPERIMENTAL`, `SYNTHETIC_ONLY`, `NOT VALIDATION OR PRODUCTION AUTHORIZATION`; use `A0_SYNTHETIC` when assurance is shown.
- Proof validity is not telemetry truth; separate source assurance, independent typed verification, publication and the relying party's decision. Do not claim safety, compliance, interoperability, demand, MVP or production readiness without direct accepted evidence.
- Maintain offline independent verification, authenticated canonical security inputs, failure-closed version/trust behavior, and observational-only operation.

## Decisions and handoff
- Update owning documents for substantive decisions, not redundant registers or ADRs for each experiment; keep GitHub history/review evidence.
- Obtain explicit authorization for policy/license changes, external or irreversible actions, hardware, real data, merge, deployment, and any promotion of experimental evidence.
- AGENTIC-INTERACTION-01: at a stopping point report completed work, next action and named blocker; offer an actionable `Continuă` control when no new decision is needed or a precise approval control when it is. Never infer a separate gate approval from a generic continuation.
- Resume from the last verified current checkpoint and do not redo completed steps.
